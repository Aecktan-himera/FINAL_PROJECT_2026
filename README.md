# Трекер задач для командной разработки

## 1. Описание проекта

### Что делает приложение

Приложение представляет собой веб-платформу для управления задачами, построенная по канбан-методологии. Она позволяет командам создавать проекты, визуализировать рабочий процесс на досках с колонками, детализировать задачи, отслеживать их статус и обмениваться комментариями. Пользователи с соответствующими правами могут распределять нагрузку, контролировать сроки и анализировать продуктивность. 

**Главные возможности ("фичи") приложения:**
  1. Полнотекстовый поиск по задачам и проектам; 
  2. Система уведомлений;
  3. Многоуровневая система ролей пользователей;
  4. Технология drag-n-drop для досок проектов;
  5. Вложенная структура проектов и задач (можно создавать подпроекты и подзадачи)
  6. Дашборд с аналитикой;
  7. Интеграция с GIT;
  8. Интеграция с Zoom.

### Для кого и какую задачу решает
Инструмент ориентирован на небольшие и средние продуктовые команды, работающие по Agile. Платформа подходит как для отдела разработчиков в одной компании, так и для группы фрилансеров или старт-апа. Приложение решает проблему прозрачности: руководитель видит, кто чем занят и на каком этапе находится каждая задача, а исполнители чётко понимают свой фронт работ и приоритеты. Платформа заменяет разрозненные таблицы и чаты, собирая всю информацию в единой среде с ролевым доступом и историей изменений.

### Ключевая ценность
Система предотвращает потерю требований, дублирование усилий и срыв сроков за счёт централизованного хранилища, автоматических уведомлений, прозрачного назначения ответственных и аналитических дашбордов.

## 3. Основные пользовательские сценарии (User Stories)
### 1. Аутентификация и профиль

**1.1. Регистрация и активация**
- *Как* `new_user`, *я хочу* зарегистрироваться с email и паролем, *чтобы* получить доступ к платформе.
  - **Действие:** отправка формы регистрации → создаётся запись в `users` с ролью `new_user` и `is_active = true`.
  - **Ограничение:** доступ к проектам и доскам отсутствует. При входе показывается уведомление об ожидании активации администратором.
- *Как* `admin`, *я хочу* видеть список всех пользователей и менять роль `new_user` на `verified_user`, *чтобы* активировать учётные записи.
  - **Действие:** в админ-панели изменение поля `role` в таблице `users`.

**1.2. Вход и управление сессией**
- *Как* любой зарегистрированный пользователь, *я хочу* входить по email и паролю, *чтобы* получать JWT-токены.
  - **Действие:** проверка `users.password_hash`, выпуск access и refresh токенов. Refresh-токен сохраняется в `tokens` (связь с пользователем).
- *Как* пользователь, *я хочу* автоматически обновлять истёкший access-токен через refresh-токен, *чтобы* оставаться в системе без повторного ввода пароля.

**1.3. Редактирование профиля и навыков**
- *Как* `verified_user`, *я хочу* редактировать имя, аватар, био, местоположение и список навыков (JSONB в `users.skills`), *чтобы* делиться информацией с командой.

---

### 2. Управление проектами и участниками

**2.1. Создание проекта и подпроекта**
- *Как* `team_lead` (или `admin`), *я хочу* создать новый проект, *чтобы* организовать работу команды.
  - **Действие:** создание записи в `projects` (владелец – текущий пользователь). Можно указать родительский проект (`parent_project_id`), создавая иерархию.
- *Как* `team_lead`, *я хочу* создать подпроект внутри существующего, *чтобы* разбить крупный проект на модули.
  - **Действие:** создание `projects` с указанием `parent_project_id`.

**2.2. Управление командой проекта**
- *Как* `team_lead` (владелец или имеющий роль `team_lead` в проекте), *я хочу* приглашать пользователей в проект и назначать им проектную роль (`project_role`), *чтобы* сформировать команду.
  - **Действие:** добавление записей в `project_members`. Приглашённый `verified_user` получает роль `developer` или `viewer`.
- *Как* `verified_user`, *я хочу* видеть список проектов, в которых я участвую, *чтобы* быстро переключаться между ними.
  - **Действие:** запрос к `project_members` с фильтром по `user_id`.

---

### 3. Доски, колонки и задачи

**3.1. Управление доской и колонками**
- *Как* `team_lead` (или `developer` с правами), *я хочу* создать доску в проекте и настроить на ней колонки (название, цвет, WIP-лимиты), *чтобы* визуализировать рабочий процесс.
  - **Действие:** создание `boards` и связанных `columns`.

**3.2. Создание задачи и подзадачи**
- *Как* `developer` или `team_lead`, *я хочу* создать задачу в колонке доски, *чтобы* зафиксировать требование.
  - **Действие:** вставка в `tasks` с указанием `board_id`, `column_id`, приоритета, дедлайна, тегов (через `task_tags`).
- *Как* `developer`, *я хочу* внутри задачи создать несколько подзадач (checklist), *чтобы* детализировать шаги выполнения.
  - **Действие:** создание `tasks` с `parent_task_id`, указывающим на родительскую задачу. Подзадачи не привязаны к колонке (`column_id = NULL`), а используют флаг `is_completed`.

**3.3. Работа с канбан-доской**
- *Как* `developer`, *я хочу* перетаскивать свои задачи между колонками, *чтобы* отразить прогресс.
  - **Действие:** обновление `tasks.column_id` и `tasks.position` (дробный индекс). Проверка прав: `developer` может двигать только назначенные на него задачи, `team_lead` – любые.
- *Как* `team_lead`, *я хочу* назначать исполнителя (assignee) на любую задачу, *чтобы* распределить нагрузку.
  - **Действие:** обновление `tasks.assignee_id`. Автоматически создаётся уведомление (`notifications`) для исполнителя.

**3.4. Детали задачи и теги**
- *Как* `developer`, *я хочу* просматривать и редактировать описание, приоритет, сроки, добавлять/удалять теги, *чтобы* актуализировать информацию.
  - **Действие:** работа с полями `tasks` и связью `task_tags`.

---

### 4. Комментарии, уведомления и история

**4.1. Комментирование и упоминания**
- *Как* участник проекта, *я хочу* оставлять комментарии к задаче, используя @username для упоминания коллег, *чтобы* обсуждать детали.
  - **Действие:** создание записи в `comments`. При обнаружении @username проверяется наличие пользователя в проекте, и ему отправляется уведомление (`notifications`) с типом `comment_added`.

**4.2. Уведомления в реальном времени**
- *Как* любой пользователь, *я хочу* получать мгновенные уведомления (в интерфейсе и на почту) о назначении задачи, новых комментариях, приглашениях на встречи, *чтобы* своевременно реагировать.
  - **Действие:** сервер при возникновении события вставляет запись в `notifications` и через WebSocket отправляет событие клиенту. Для email используется отдельный микросервис или модуль, читающий ту же таблицу.

**4.3. История изменений задачи**
- *Как* `team_lead`, *я хочу* видеть, кто и когда менял статус, исполнителя, приоритет, *чтобы* аудировать изменения.
  - **Действие:** запись в `task_history` при каждом обновлении значимых полей задачи.

---

### 5. Поиск и аналитика

**5.1. Полнотекстовый поиск по задачам**
- *Как* участник проекта, *я хочу* искать задачи по ключевым словам в заголовке и описании, *чтобы* быстро находить нужную информацию.
  - **Действие:** запрос к `tasks` с использованием полнотекстового индекса (tsvector).

**5.2. Дашборд аналитики**
- *Как* `team_lead`, *я хочу* видеть burndown-диаграмму, тепловую карту активности команды и прогноз завершения спринта, *чтобы* контролировать темп работ.
  - **Действие:** агрегация данных из `tasks`, `task_history` (для отслеживания перемещений по колонкам). Прогноз строится на основе линейной регрессии по истории закрытых задач.

---

### 6. Управление встречами и интеграция с Zoom

**6.1. Планирование встречи**
- *Как* `team_lead` или `developer`, *я хочу* создать встречу, привязанную к задаче или проекту, указав участников, дату и время, *чтобы* обсудить рабочие вопросы.
  - **Действие:** создание записи в `meetings`. Участники добавляются в `meeting_participants`. Система автоматически отправляет уведомление (`notifications`) с типом `meeting_invitation`.

**6.2. Интеграция с Zoom**
- *Как* организатор, *я хочу*, чтобы при создании встречи автоматически генерировалась Zoom-конференция и ссылки добавлялись в описание встречи, *чтобы* не делать это вручную.
  - **Действие:** серверный модуль через Zoom API (используя общий сервисный аккаунт) создаёт встречу и сохраняет `zoom_meeting_id`, `zoom_join_url`, `zoom_start_url` в таблице `meetings`.

**6.3. Просмотр календаря**
- *Как* участник, *я хочу* видеть календарь с запланированными встречами по проекту, *чтобы* не пропустить созвоны.
  - **Действие:** запрос к `meetings` с фильтром по проекту и датам.

**6.4. Реагирование на приглашение**
- *Как* участник, *я хочу* принять, отклонить или предварительно подтвердить участие во встрече, *чтобы* организатор знал, кто придёт.
  - **Действие:** обновление `meeting_participants.response_status`.

---

### 7. Интеграция с GitHub

**7.1. Подключение репозитория к проекту**
- *Как* `team_lead`, *я хочу* привязать GitHub-репозиторий к проекту, *чтобы* видеть commit'ы и pull request'ы непосредственно в трекере.
  - **Действие:** добавление записи в `git_repositories`. Опционально настраивается webhook для автоматического получения событий.

**7.2. Связывание веток и задач**
- *Как* разработчик, *я хочу* создать ветку в репозитории, название которой включает ID задачи (например, `feature/TASK-42`), *чтобы* система автоматически связала ветку с задачей.
  - **Действие:** при поступлении вебхука о создании ветки сервер ищет ID задачи в названии и вставляет запись в `git_branches` с `task_id`.

**7.3. Отслеживание pull request'ов**
- *Как* `team_lead`, *я хочу* видеть статус PR, связанного с задачей (открыт/закрыт/влит), и автоматически перемещать задачу в колонку «Done» при мерже.
  - **Действие:** вебхук обновляет `git_pull_requests.state`. При `state = 'merged'` сервер может обновить `tasks.column_id` на ID колонки «Done» (если настроено).

**7.4. Просмотр истории коммитов**
- *Как* `developer`, *я хочу* видеть список коммитов, привязанных к задаче, *чтобы* быстро оценить прогресс по коду.
  - **Действие:** запрос к `git_commits` по `task_id`.

**7.5. Авторизация через GitHub**
- *Как* пользователь, *я хочу* подключить свой GitHub-аккаунт, *чтобы* действия с репозиториями выполнялись от моего имени (создание веток, PR).
  - **Действие:** OAuth flow, сохранение зашифрованного токена в `git_user_tokens`.

---

### 8. Администрирование системы

**8.1. Управление пользователями**
- *Как* `admin`, *я хочу* просматривать список всех пользователей, изменять системные роли, блокировать аккаунты (установка `is_active = false`), *чтобы* контролировать доступ к платформе.

**8.2. Мониторинг активности**
- *Как* `admin`, *я хочу* видеть общую статистику: количество активных проектов, задач, пользователей, *чтобы* оценивать нагрузку на систему.

### Ключевые связи и индексы

- **Иерархии**  
  `projects.parent_project_id` – подпроекты.  
  `tasks.parent_task_id` – подзадачи (один уровень).  
  Обе реализованы ссылкой на собственную таблицу.

- **Позиционирование задач**  
  Поле `tasks.position` VARCHAR (fractional index) обеспечивает лёгкое перемещение без массовых обновлений.

- **Индексы для производительности**
  - `idx_tasks_board_column` на `tasks(board_id, column_id)`
  - `idx_tasks_assignee` на `tasks(assignee_id)`
  - `idx_tasks_parent` на `tasks(parent_task_id)`
  - `idx_notifications_user_read` на `notifications(user_id, is_read)`
  - `idx_meetings_project_time` на `meetings(project_id, start_time, end_time)`
  - `idx_git_commits_task` на `git_commits(task_id)`
  - Полнотекстовый индекс для поиска по задачам (GIN на `to_tsvector`).

## 5. Список ключевых экранов приложения
### 1. Аутентификация и профиль

#### 1.1. Страница входа
- **Маршрут:** `/login`
- **Назначение:** Вход в систему по email и паролю.
- **Элементы:** Форма (email, пароль), кнопка «Войти», ссылка на страницу регистрации.
- **Доступ:** Все неавторизованные пользователи.

#### 1.2. Страница регистрации
- **Маршрут:** `/register`
- **Назначение:** Создание учётной записи с ролью `new_user`.
- **Элементы:** Форма (username, email, пароль, имя, фамилия), кнопка «Зарегистрироваться».
- **После успеха:** Перенаправление на страницу входа с уведомлением об ожидании активации.

#### 1.3. Личный профиль
- **Маршрут:** `/profile`
- **Назначение:** Просмотр и редактирование своих данных, просмотр достижений (геймификация).
- **Элементы:**
  - Аватар, поля: имя, фамилия, email (нередактируемый), username, bio, location, skills (редактируемые).
  - Кнопка «Сохранить».
  - Секция «Мои достижения» (если реализована геймификация).
- **Доступ:** Все активированные пользователи (`verified_user`, `team_lead`, `admin`). Для `new_user` доступна, но с сообщением об ожидании активации.

---

### 2. Управление проектами и участниками

#### 2.1. Дашборд проектов
- **Маршрут:** `/projects`
- **Назначение:** Показать все проекты, в которых участвует пользователь (с учётом проектных ролей).
- **Элементы:**
  - Сетка/список карточек проектов. Каждая карточка: название, ключ, описание, роль пользователя.
  - Кнопка «Создать проект» (видна только `team_lead` и `admin`).
  - Фильтр по роли/активности.
- **Взаимодействие:** Клик по карточке → переход на доску проекта (или на страницу проекта).
- **Доступ:** `verified_user`, `team_lead`, `admin` (`new_user` перенаправляется на профиль с предупреждением).

#### 2.2. Страница проекта (настройки и участники)
- **Маршрут:** `/projects/:projectId`
- **Назначение:** Детальное управление конкретным проектом.
- **Элементы:**
  - Вкладки: «Доски», «Участники», «Настройки», «Подпроекты», «Аналитика», «Встречи».
  - **Вкладка «Участники»:** таблица участников с ролями (`owner`, `team_lead`, `developer`, `viewer`). Кнопки «Пригласить» (только для `team_lead` и `owner`), «Изменить роль», «Удалить». Модальное окно «Пригласить пользователя» (поиск по email/username).
  - **Вкладка «Настройки»:** Изменение названия, описания, ключа, видимости. Для `owner` и `team_lead`.
  - **Вкладка «Подпроекты»:** список дочерних проектов, кнопка «Создать подпроект». Древовидное отображение.
- **Доступ:** Участники проекта видят базовую информацию, но управление — согласно проектной роли.

#### 2.3. Создание / редактирование проекта
- **Модальное окно** (вызывается с дашборда или страницы проекта).
- **Элементы:** Название, ключ (генерируется автоматически, можно изменить), описание, родительский проект (опционально, выбор из своих проектов).
- **Доступ:** `team_lead`, `admin`.

### 3. Доски и задачи (канбан-пространство)

#### 3.1. Доска проекта (Kanban Board)
- **Маршрут:** `/projects/:projectId/boards/:boardId`
- **Назначение:** Отображение доски с колонками и задачами, основной рабочий инструмент.
- **Элементы:**
  - **Хедер доски:** Название доски, кнопка выбора досок (если их несколько), кнопка «Добавить колонку» (для `team_lead`).
  - **Колонки:** Горизонтальный список, каждую можно перетаскивать (изменение порядка). Заголовок колонки с цветовой меткой и WIP-лимитом (если задан).
  - **Карточки задач внутри колонок:** Показывают заголовок, приоритет (цветной индикатор), аватар исполнителя, количество комментариев, бейджи (теги, GitHub PR). Поддерживают drag-and-drop между колонками.
  - **Фильтры** (над доской): По исполнителю, тегам, приоритету, поисковой строке.
- **Взаимодействие:**
  - Перетаскивание карточек (на бэкенд: `PATCH /tasks/:id/move`). `developer` может перемещать только свои задачи, `team_lead` – любые.
  - Клик по карточке → модальное окно задачи.
  - Кнопка «+» в колонке → создание новой задачи в этой колонке.
- **Доступ:** Все участники проекта (просмотр). Создание, редактирование задач — в соответствии с проектной ролью.

#### 3.2. Модальное окно задачи (или отдельная страница)
- **Маршрут:** `/tasks/:taskId` (может быть страницей) или модально.
- **Назначение:** Полная информация о задаче, подзадачи, комментарии, история.
- **Элементы:**
  - **Панель свойств:** Заголовок (редактируемый), описание (markdown), приоритет, дедлайн (датапикер), теги (добавление/удаление), исполнитель (выпадающий список участников проекта), статус (колонка).
  - **Вкладки:**
    - *«Подзадачи»*: Список дочерних задач с чекбоксами (`is_completed`). Кнопка «Добавить подзадачу». Прогресс-бар.
    - *«Комментарии»*: Лента комментариев, форма отправки, поддержка @упоминаний (автодополнение). Каждый комментарий с аватаром автора и временем.
    - *«История изменений»*: Лог изменений полей (из `task_history`).
  - **Действия:** Кнопки «Удалить задачу» (автор или `team_lead`), «Создать встречу» (открывает форму создания встречи, привязанной к задаче).
  - **Кнопки навигации:** Следующая/предыдущая задача на доске.
- **Доступ:** Просмотр — все участники. Редактирование полей — `developer` (свои задачи или все в зависимости от роли), `team_lead` — любые задачи. Назначение исполнителя — `team_lead`, `developer` может только назначить себя (опционально).

#### 3.3. Создание задачи (быстрое)
- **Модальное окно или форма в колонке**
- **Элементы:** Заголовок, приоритет, теги, дата завершения (опционально). Кнопка «Создать» (задача сразу попадает в выбранную колонку).
- **Доступ:** `developer` и выше.

### 4. Коммуникации и уведомления

#### 4.1. Панель уведомлений (глобальная)
- **Иконка колокольчика в хедере** с бейджем непрочитанных.
- **Выпадающий список уведомлений:** Каждое уведомление — тип (иконка), сообщение, время. При клике — переход к задаче/встрече/комментарию.
- **Действия:** Кнопка «Отметить прочитанным» у каждого, кнопка «Прочитать все».

- **Действие:** Клик по toast открывает соответствующий объект.

### 5. Встречи и календарь

#### 5.1. Календарь проекта
- **Маршрут:** `/projects/:projectId/calendar`
- **Назначение:** Просмотр встреч проекта (и личных) в календарном виде.
- **Элементы:**
  - Календарь (месяц/неделя/день) — используется библиотека `react-big-calendar`.
  - События отображаются как блоки с названием встречи, временем.
  - Клик по событию → детали встречи.
  - Кнопка «Создать встречу» → модальное окно создания.
- **Доступ:** Участники проекта.

#### 5.2. Детали встречи
- **Модальное окно (или страница)**
- **Элементы:** Тема, описание, дата/время начала и конца, список участников со статусами (`pending`, `accepted` и т.д.), ссылка на Zoom (если создана).
- **Действия:** Принять/отклонить участие, редактировать встречу (организатор), удалить встречу (организатор).
- **Доступ:** Участники встречи (просмотр), организатор (управление).

#### 5.3. Создание / редактирование встречи
- **Модальное окно**
- **Элементы:** Тема (по умолчанию название задачи, если создаётся из задачи), дата/время (два датапикера), длительность, описание, выбор участников (из участников проекта). Чекбокс «Создать Zoom-конференцию» (включён по умолчанию).
- **Действие:** После сохранения — автоматическое создание в Zoom (на бэке), рассылка уведомлений участникам.
- **Доступ:** `team_lead` и `developer` (может создавать встречи по задаче).

### 6. Интеграция с GitHub

#### 6.1. Настройки GitHub репозитория проекта
- **Маршрут:** Внутри страницы проекта, вкладка «Интеграции» или «GitHub».
- **Элементы:**
  - Список подключённых репозиториев (кнопка «Добавить репозиторий»).
  - Добавление: ввод `owner/repo`, настройка webhook (опционально).

- **Доступ:** `team_lead` (owner).

- **Доступ:** Любой пользователь (для личных интеграций).

#### 6.3. Отображение PR и коммитов в задаче
- **В модальном окне задачи** — дополнительная вкладка «GitHub».
- **Элементы:**
  - **Pull Requests:** список связанных PR с бейджами состояния, ссылкой на GitHub.
  - **Коммиты:** Блок с коммитами, относящимися к задаче (по связи через `git_commits.task_id`).
- **Доступ:** Участники проекта.

  - **Прогноз завершения спринта** (линейная регрессия).
  - **Распределение задач по исполнителям** (круговая диаграмма).
  - **Среднее время цикла задачи**.
- **Доступ:** `team_lead`, `owner`. `developer` может видеть упрощённую версию.

### 8. Администрирование

#### 8.1. Административная панель
- **Маршрут:** `/admin` (только для роли `admin`).
- **Вкладки:**
  - **Пользователи:** Таблица всех пользователей с фильтрацией по роли, статусу. Колонки: username, email, fullname, системная роль, is_active. Действия: изменить роль (выпадающий список), заблокировать/разблокировать (переключение `is_active`).
  - **Общая статистика:** Количество проектов, активных задач, пользователей, встреч. Графики регистраций по дням.
- **Доступ:** `admin`.

#### 8.2. Модальное окно подтверждения активации пользователя
- **Вызывается из панели администратора при смене роли** `new_user` → `verified_user`. Может быть просто переключением.
